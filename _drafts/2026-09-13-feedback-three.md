# ① 하네스 과제 — 재시도 정책

## [원문]

> 사용자 요구를 A01~A12와 실제 세션·파일 변경·검사 결과에 연결하고, 모의 검증과 실제 모델 검증을 구분했습니다. 수정 제안만 하고 끝나거나 pytest 실패를 성공으로 기록했던 사례를 숨기지 않고 승인 전 검사·files_changed·기록 수정으로 이어간 점이 좋습니다. 같은 10문항·모델·한도에서 재시도 0→2만 바꾸어 공식 통과 0/10은 그대로지만 검사 28→61/304, 서버 오류 9→5로 변한 결과와 blockchain 8→1의 퇴보까지 분석하여 세 기준을 충족합니다. 다음에는 같은 조건을 반복·순서 교차하여 서버 변동과 재시도 효과를 분리하고, 400/422 같은 수정 없는 재요청과 일시적 연결 오류·429/5xx를 구분해 재시도 정책을 검증하세요. 일부 검사 통과와 작업 완료를 구분한 현재 보고 방식을 유지하면 개선 효과를 더 명확히 판단할 수 있습니다.

## [분석]

### 성격 — 결함 지적이 아니다

문장별로 나누면 이렇다.

| 문장 | 성격 |
|---|---|
| 요구를 A01~A12와 실제 결과에 연결, 모의·실제 구분 | 관찰 (루브릭 3번 충족 확인) |
| 실패 사례를 숨기지 않고 조치로 이어간 점 | **칭찬** |
| "…분석하여 **세 기준을 충족합니다**" | **판정 — 통과** |
| "**다음에는** … 분리하고 … 검증하세요" | 다음 단계 제안 (유일한 요구) |
| "현재 보고 방식을 **유지하면**" | 유지 권고 = 건드리지 말 것 |

**이번 제출물에 고치라는 지적은 없다.** "다음에는"으로 시작하는 한 문장이 전부다.

### 제안 ⑴ 반복·순서 교차 — 무엇을 가르려는 것인가

내 실험은 이렇게 놓여 있었다.

```
13:41 ─ 기준 실행 37분 ─ 14:18
                         23초
14:18 ─ 개선 실행 37분 ─ 14:56
```

두 실행이 **시간 순서로** 놓여서, 결과 차이에 두 가지가 섞인다.

| 섞인 것 | 내용 |
|---|---|
| 재시도 효과 | 재고 싶었던 것 |
| 서버 상태 변동 | Colab GPU가 뒤로 갈수록 달라졌을 수 있음 (온도·다른 사용자·네트워크) |

23초 간격은 이 영향을 **줄이려는** 시도였지 없애지는 못한다.

**순서 교차** — 기준→개선 한 벌, 개선→기준 한 벌. 두 벌에서 같은 방향으로 움직이면 재시도 효과이고, 한쪽에서만 나타나면 시간 순서 탓이다.

**반복 3회** — 우연을 줄인다. blockchain이 세 번 중 한 번만 퇴보하면 변덕, 세 번 다 퇴보하면 재시도 탓이다.

내가 보고서에 이미 이렇게 적어뒀었다. **퍼실이 그걸 확인해주고 방법을 준 것이다.**

> blockchain의 퇴행이 재시도 때문인지 모델의 변덕인지 이 데이터로는 가릴 수 없다.

### 제안 ⑵ 재시도 분류 — 진단은 맞고 처방이 거칠었다

| 단계 | 내용 | 판정 |
|---|---|---|
| 내가 찾은 원인 | "HTTP 400에 두 번 재시도하며 6초를 버렸다" | **맞음** |
| 내가 세운 처방 | "**4xx는 전부** 재시도 안 함" | **너무 넓음** |
| 퍼실의 처방 | "400/422 같은 **수정 없는 재요청**과 일시적 연결 오류·**429**/5xx를 구분" | 정확 |

**차이는 429 하나다.**

```
429 Too Many Requests
  번호는 4xx   → 형식상 '요청 쪽 문제'
  실제 성격    → 요청 내용이 아니라 타이밍 문제
  다시 보내면  → 기다렸다 그대로 보내면 통함
```

내 기준대로 뒀다면 **호출량 제한에 걸렸을 때 재시도 없이 포기**했을 것이다. 무료 API나 공유 서버에서 흔한 상황이다.

퍼실의 표현이 정확하다 — **"수정 없는 재요청"**. 기준은 번호대가 아니라 **요청을 고쳐야 하는가** 다.

### 조치 (2026-09-13)

| 항목 | 상태 |
|---|---|
| 보고 방식 (검사 통과 ≠ 작업 완료) | **건드리지 않음** — 요구대로 |
| 재시도 분류 정밀화 | **고침** — `providers.is_retryable()`, 테스트 7건, 전체 105건 통과 |
| 반복·순서 교차 재측정 | **NOT_RUN** — 약 7.4시간, Colab 무료 세션 한도(3시간 40분) 초과 |

고친 뒤 기준표는 이렇다.

| 재시도 **안 함** | 재시도 **함** |
|---|---|
| 400·401·403·404·405·409·413·422 | **408·429**·5xx 전부·연결 끊김·타임아웃 |

A11·A12에 기록된 수치는 **수정 이전 코드로 잰 것**이라 그대로 뒀다. 고친 것과 확인한 것은 다른 사건이다.

### 인용 가능한 수치

- 공식 통과 0/10 → 0/10 (안 움직임)
- 검사 통과 28/304 → 61/304 (2.2배)
- 서버 오류로 중단 9건 → 5건
- 파일을 만든 문항 4 → 10
- blockchain 8/10 → 1/10 (퇴보)
- 바꾼 것: `max_provider_retries` 0→2 **하나**, 코드 파일·manifest SHA256 동일
- 두 실행 간격 23초, 각 37분
- 테스트 86건 → 105건

### 남는 교훈 (글의 축이 될 만한 것)

**진단이 맞아도 처방이 틀릴 수 있다.**

"400에 재시도한 게 문제다"까지는 기록을 보고 정확히 찾았다. 그런데 거기서 **"그럼 4xx를 다 빼자"** 로 간 건 한 발 더 나간 일반화였다. 사례 하나(400)를 보고 범주 전체(4xx)로 넓혔고, **그 범주 안에 성격이 다른 게 있는지 확인하지 않았다.**

`provider_protocol` 이라는 이름 하나에 400과 502를 묶어둔 것과 **같은 실수를 한 단계 위에서 반복한 셈**이다. 이름이 하나라고 안에 든 게 하나는 아니다.

## [초안] — 참고용, 다시 써도 된다

> ⚠️ 세 피드백을 다 보고 나면 강조점이 달라질 수 있다. 이 문장에 끌려가지 말 것.

```markdown
## N. 하네스 과제 피드백 — 4xx를 통째로 자른 게 틀렸다

며칠 전 만든 [에이전트 하네스](/blog/posts/twice-the-checks-still-zero/)에 대한 피드백을 받았다.

좋게 봐준 대목은 이랬다. 요구사항을 실제 세션·파일 변경·검사 결과에 연결한 것,
모의 검증과 실제 모델 검증을 나눠 표시한 것, **수정 제안만 하고 끝나거나 테스트
실패를 성공으로 기록했던 사례를 숨기지 않고** 고친 과정으로 이어간 것.

그리고 다음에 할 것을 두 가지 짚어줬다.

> 같은 조건을 **반복·순서 교차**하여 서버 변동과 재시도 효과를 분리하고,
> 400/422 같은 **수정 없는 재요청**과 일시적 연결 오류·**429**/5xx를 구분해
> 재시도 정책을 검증하세요.

두 번째 문장에서 멈췄다. **429가 거기 들어가 있었다.**

### 내가 적어둔 기준이 틀렸다

실험 보고서의 "다음에 할 것"에 이렇게 써뒀다.

> 4xx(요청 자체가 잘못됨)는 재시도하지 않는다. 5xx와 연결 끊김·타임아웃만 재시도한다.

그럴듯해 보였다. 4xx는 "네 요청이 잘못됐다"이고 5xx는 "내 서버가 문제다"니까,
전자는 다시 보내도 소용없고 후자는 기다리면 통한다 — 이렇게 나눴다.

**429가 그 선을 넘어간다.**

> **알고 가기 — 429 Too Many Requests**
> "요청이 너무 잦다"는 뜻이다. 번호는 4xx 대역이라 형식상 '요청 쪽 문제'로 분류되지만,
> **요청 내용이 잘못된 게 아니라 타이밍이 문제다.** 잠시 기다렸다 같은 요청을 그대로
> 보내면 통한다.
>
> 회선 점유율이 100%일 때 패킷이 드롭되는 것과 비슷하다. **패킷이 잘못된 게 아니라
> 지금 보낸 게 문제**라, 조금 뒤 같은 패킷을 다시 보내면 나간다.

내 기준대로 두면 호출량 제한에 걸렸을 때 **재시도 없이 그냥 포기**한다.
번호대로 자른 게 문제였다. 기준은 **"고치지 않고 다시 보내면 답이 달라지는가"** 여야 했다.

### 고친 것

오류 객체에 HTTP 상태를 실어 보내고, 판정을 상태 코드로 옮겼다.
그전에는 오류 종류 이름 하나만 보고 있었는데, 그 이름 아래에
`400`(컨텍스트 초과)과 `502`(서버가 잠깐 죽음)가 같이 들어 있었다.

실제로 그 때문에 한 문항이 망가졌었다. 컨텍스트 한도를 넘긴 요청을
**두 번 더 보내며 6초를 버렸고**, 검사 통과가 8/10에서 1/10로 떨어졌다.

회귀 테스트를 일곱 개 붙였다. 그중 둘이 이 사례를 직접 고정한다 —
**400이면 재시도 없이 끝나는가**, **429면 재시도해서 회복하는가**. 전체 105건이 통과한다.

### 못 고친 것

피드백의 앞쪽 절반, **반복·순서 교차 재측정은 하지 않았다.**

한 번 실행이 37분이다. 반복 3회에 순서 교차까지 하면 **7.4시간**이고,
쓸 수 있는 무료 GPU 세션 한도가 3시간 40분이다. 한 번에 안 들어간다.

그래서 계획만 문서에 적고 **NOT_RUN**으로 남겼다. 그리고 한 줄을 덧붙였다.

> 이 수정이 10문항 점수를 어떻게 바꾸는지는 확인하지 못했다.
> 기록된 수치는 수정 **이전** 코드로 측정한 것이며 그대로 둔다.

코드를 고쳤다고 옛 측정값을 새 코드의 결과처럼 만들면 안 된다.
**고친 것과 확인한 것은 다른 사건이다.**

### 남는 것

피드백이 마지막에 이렇게 닫혔다.

> 일부 검사 통과와 작업 완료를 구분한 현재 보고 방식을 유지하면
> 개선 효과를 더 명확히 판단할 수 있습니다.

점수가 0이라 초라해 보여서 검사 숫자를 앞세우고 싶었던 대목인데, 나누길 잘했다.

그리고 하나 더 남았다. **진단이 맞아도 처방이 틀릴 수 있다는 것.**
"400에 재시도한 게 문제다"까지는 기록을 보고 찾았는데, 거기서 "그럼 4xx를 다 빼자"로
간 건 한 발 더 나간 일반화였다. 사례 하나를 보고 범주 전체로 넓혔고,
그 안에 성격이 다른 게 있는지는 확인하지 않았다.

`provider_protocol`이라는 이름 하나에 400과 502를 묶어둔 것과 같은 실수를
한 단계 위에서 반복한 셈이다. **이름이 하나라고 안에 든 것도 하나는 아니다.**
```
