> 이어지는 글: [내가 쓴 설명서는 나만 따라갈 수 있었다](/blog/posts/my-manual-only-worked-for-me/)에서 내 문서만 들고 다른 컴퓨터에서 따라해보다 첫 줄부터 막혔다. 그 글 첫 절의 제목이 **"내가 한 검증은 검증이 아니었다"**였다. 오늘 같은 벽을 다시 만났다. 다만 이번엔 문서를 넘긴 상대가 남이 아니라 **나 자신**이었고, 검증이 아니었던 것도 내 손이 아니라 **도구의 보고**였다.
{: .prompt-info }

> 2026년 8월 16일 밤부터 17일까지의 기록이다.
{: .prompt-info }

지난 글의 예고는 복약 알림 앱의 자연어 읽기를 되살리는 것이었다. **그건 그대로 있다.** 오늘은 다른 책상에 앉았다.

앞으로 해커톤에 나갈 생각이다. 팀으로 붙으면 한 저장소를 여러 사람이, 여러 컴퓨터에서, 각자의 계정으로 만지게 된다. 그게 실제로 굴러가는지 **미리 밟아보고 싶었다.**

그래서 이미 돌아가고 있는 새록이를 실험 대상으로 삼았다. 리눅스 데스크탑은 운영 서버로 두고, 윈도우 노트북에서 개발해 깃허브로 주고받았다. 클로드코드는 계정을 두 개 썼다 — 한쪽이 사용량 한도에 걸리면 다른 계정으로 갈아탔다.

결론부터 적으면, **코드는 문제없이 오갔다.** 문제는 코드가 아닌 것들이었다.

## 1. 이삿짐은 갔는데 기억은 안 갔다

데스크탑에서 작업을 마치고 노트북에서 새 세션을 열었다. 당연히 아까 하던 대화가 목록에 있을 줄 알았다.

없었다.

목록에 뜨는 세션 서른 개가 전부 노트북에서 만든 것이었고, 작업 폴더도 전부 윈도우 경로였다. 리눅스에서 만든 건 하나도 없었다.

> **알고 가기 — 세션은 계정에 딸린 게 아니다**
> 클로드코드의 대화 기록은 그 컴퓨터의 디스크(`~/.claude/projects/`) 안에만 쌓인다. 계정으로 로그인해도 대화가 서버에서 내려오지 않는다.
>
> 이삿짐 센터를 부른 것과 비슷하다. 가구는 새 집에 도착했는데, **그 집에서 무슨 이야기를 하며 살았는지는 아무도 싣고 오지 않았다.** 짐만 옮겨진다.
{: .prompt-tip }

같은 계정인데도 그렇다. 이게 첫 함정이었고, 해커톤에서 팀원과 화면을 나눠도 대화는 안 넘어간다는 뜻이다.

## 2. 그래서 인수인계서를 썼다

방법은 하나뿐이었다. **넘겨야 할 것을 문서로 적어 깃허브에 밀어넣는 것.**

다행히 데스크탑에서 작업을 끝낼 때 그걸 해뒀다. `docs/handoff.md`. 마지막 커밋이 하필 "노트북 WSL 인계 메모 추가"였다.

거기에는 이런 것들이 적혀 있었다.

| 적어둔 것 | 왜 필요했나 |
|---|---|
| 지금 서비스가 어디서 어떻게 돌고 있는지 | 노트북에서는 볼 수 없다 |
| git에 없는 것 (비밀값, DB, 로컬 설정) | `.gitignore` 처리돼 안 넘어온다 |
| **노트북에서 절대 하지 말 것** | 같은 터널 토큰을 두 기기에서 켜면 트래픽이 갈린다 |
| 3주 전에 왜 작업이 끊겼는지 | 검증 직전에 세션이 끊겨 커밋이 없었다 |

세 번째 줄이 특히 그렇다. **문서가 아니면 전달할 방법이 없는 종류의 정보**다. 코드를 읽어도 "이걸 두 기기에서 켜면 안 된다"는 건 안 나온다.

이 파일 하나로 3주 전 맥락까지 복구됐다. 여기까지는 성공이었다.

## 3. 그 인수인계서가 틀려 있었다

인계 메모의 "다음 할 일" 항목에 이렇게 적혀 있었다.

> 2주차 콘텐츠 — `questions-week2.json`. 1주차와 같은 형식으로 **파일만 추가하면 된다.** 앱 코드는 건드릴 필요 없다.

그 문장을 믿고 시작했다. 그런데 실제 코드를 열어보니 달랐다.

- 콘텐츠 파일 이름이 `questions-week1.json`으로 **코드에 박혀** 있었다
- 세션을 내려주는 함수가 항상 `days[0]`, 즉 **1일차만** 꺼내고 있었다
- 완료 화면의 미션도 늘 1일차 것이었다

즉 **몇 주가 지나도 1주차 1일차만 반복해서 보여주고 있었다.** 2주차 파일을 만들어 넣어도 아무 일도 일어나지 않는 상태였다.

인계 메모를 쓴 시점에는 그게 사실이라고 믿었을 것이다. 코드를 다시 열어보지 않고 기억으로 적었기 때문에 틀렸다.

**여기서 배운 것: 인수인계서는 그 시점의 믿음을 적은 것이지, 코드의 현재 상태가 아니다.** 문서를 읽고 시작하되, 문서가 말하는 지점을 코드로 한 번 확인해야 한다. 이번엔 다행히 파일을 열어보는 습관이 걸러냈다.

## 4. "검증 완료"가 검증이 아니었다

순환 로직을 짜고 나서 보고를 받았다. 아직 안 한 일이 세 가지 — 커밋, 로컬 서버 정리, 운영 배포. 나머지는 끝난 것처럼 읽혔다.

그런데 검증 계획서에는 이런 절차가 있었다. 완료 기록을 0개에서 5개, 10개까지 늘려가며 매번 화면을 불러 **날짜가 실제로 넘어가는지** 확인하기.

그게 정말 돌아갔는지 확인하고 싶었다. 세션 기록 파일이 1.4MB 남아 있으니 뒤져보면 된다.

| 찾은 것 | 결과 |
|---|---|
| 문법 검사 통과 기록 | 있음 |
| 수정한 코드로 서버 다시 띄운 기록 | 있음 |
| 세션 화면을 불러온 횟수 | **60회** |
| 그중 응답에 "2주차"가 찍힌 횟수 | **0회** |
| 완료 기록을 억지로 늘린 기록 | **없음** |

60번을 불렀는데 전부 1주차 상태였다. **주차가 넘어가는 순간은 한 번도 실행되지 않았다.** 이번 작업의 핵심이 바로 그 부분이었는데도.

> **알고 가기 — 종료 코드는 아무것도 보장하지 않는다**
> 중간에 이런 일도 있었다. 꾸러미 설치 명령이 성공(종료 코드 0)으로 끝났는데 폴더가 없었다. 알고 보니 뒤에 붙인 `| tail` 이 성공한 것이었고, 정작 설치는 아직 진행 중이었다.
>
> 택배 기사가 "배송 완료"를 눌렀는데 문 앞에 물건이 없는 상황과 같다. **눌린 버튼이 아니라 문 앞을 봐야 한다.** 나는 파일이 실제로 있는지, 응답에 그 값이 찍혔는지를 봤다.
{: .prompt-tip }

이 발견 덕에 순환 검증을 처음부터 다시 돌렸다. 완료 일수를 0에서 11까지 한 칸씩 올리며 열두 번 불렀다.

| 완료 일수 | 주차 | 나온 문항 |
|---|---|---|
| 0 | 1 | 일주일은 며칠이에요? |
| 1~3 | 1 | 계절 · 달 · 명절 |
| 4 | 1 | 편지를 부치는 곳은 어디예요? |
| **5** | **2** | **해가 뜨면 아침이에요, 저녁이에요?** |
| 6~9 | 2 | 나이 · 국기 · 방향 · 버스 |
| 10~11 | 2 | 콘텐츠가 없어 2주차로 되돌아옴 |

열두 번 모두 다른 문항이 나왔다. 그리고 5번째에서 처음으로 "2주차"가 응답에 찍혔다. **아까 0회였던 그 값이다.**

## 5. 창을 세 개로 나눴다

작업하는 쪽과 확인하는 쪽을 나눠보기로 했다. 터미널 두 개, 그리고 데스크탑 앱 하나.

여기서 몰랐던 걸 알게 됐다. **터미널의 두 세션이 서로 대화할 수 있다.** 각 세션이 `~/.claude/sessions/` 에 자기 정보를 등록하고 소켓을 하나 열어둔다.

```
"name": "dementia-care-38",  "status": "waiting"
"messagingSocketPath": "/run/user/1000/cc-socks/2753.sock"
"peerProtocol": 1
```

실제로 효과가 있었다. 두 세션이 같은 파일을 만들려고 하던 순간, 한쪽이 옆 세션에 "혹시 2주차 콘텐츠 작업 중인가"라고 물었고 답을 받아 **중복 작성을 멈췄다.** 내가 개입하지 않았는데 알아서 갈렸다.

다만 셋이 다 이어진 건 아니었다.

| 조합 | 통신 |
|---|---|
| 터미널 ↔ 터미널 | 소켓으로 직접 |
| **데스크탑 앱 ↔ 터미널** | **안 됨** |

데스크탑 앱은 그 통신망 밖에 있었다. 그래서 내가 화면을 캡처해서 옮겨야 했다. 3단 구조가 아니라 **2단 구조 + 사람 한 명**이었던 셈이다.

역할은 이렇게 굴러갔다.

- **터미널 1** — 코드를 고친다
- **터미널 2** — 읽기 전용으로 묶어두고 옆 세션을 지켜본다
- **데스크탑 앱** — 파일을 직접 열어 실측으로 대조한다
- **나** — 배포·푸시처럼 되돌리기 어려운 것만 결정한다

두 번째 창을 읽기 전용으로 묶은 건 꼭 필요했다. 안 묶으면 두 창이 같은 파일을 동시에 고쳐 서로 덮어쓴다.

## 6. 승인 창을 닫으면 조용히 지나간다

작업하는 창이 한때 "수정을 묻지 않고 바로 적용" 모드로 켜져 있었다. 그 사이에 실서비스 코드 **90줄이 내 확인 없이** 들어갔다.

결과물은 좋았다. 주석까지 정갈하게 달려 있었고 되돌릴 일도 없었다. **그래서 더 위험하다.** 결과가 좋으면 모드가 켜져 있는 걸 눈치채지 못한다.

승인 창에서 이런 선택지를 몇 번 만났다.

| 문구 | 뜻 |
|---|---|
| `python3 -c ' *` 를 다시 묻지 않기 | 별표가 붙었다 — **이 형태로 시작하는 모든 명령**이 통과된다 |
| 이 폴더의 **비슷한 명령**을 다시 묻지 않기 | "비슷한"의 범위가 정해져 있지 않다 |
| 자동 모드로 진행 | 앞으로 안 묻는다 |

전부 거절했다. 하필 그 구간이 데이터베이스에 값을 넣었다 빼는 검증 중이었다. 거기서 창을 닫으면 무엇이 들어가고 지워졌는지 볼 기회가 사라진다.

## 7. 잔디가 안 찍혔다

마지막이 제일 조용한 함정이었다.

노트북에서 만든 커밋 세 개가 **내 계정으로 잡히지 않았다.** 커밋 목록에는 내 이름이 보이는데, 깃허브가 인식하는 작성자는 비어 있었다.

```
7484baa  author.login = 없음      marcuscho1945@gmail.com
d12f35e  author.login = 없음      marcuscho1945@gmail.com
4d959dd  author.login = nike1137-svg   (데스크탑)
```

> **알고 가기 — 깃허브는 이름을 안 보고 이메일만 본다**
> 커밋에 적힌 이름이 무엇이든 상관없다. 깃허브는 **이메일 주소로만** 계정을 찾는다. 계정에 등록되지 않은 주소로 커밋하면 이름이 맞아도 남남이 된다.
>
> 우편물에 받는 사람 이름만 정확히 쓰고 주소를 안 쓴 것과 같다. 이름을 아는 사람이 봐도 배달은 안 된다.
{: .prompt-tip }

원인을 파보니 더 얄궂었다. 커밋에 박혀 있던 주소는 **AI 도구에 로그인할 때 쓰는 계정 이메일**이었다. 화면 곳곳에 뜨는 주소라 "내 이메일"로 보이는데, **깃허브 계정과는 아무 관계가 없다.** 내 깃허브는 다른 주소로 만들었다.

그러니까 이런 상태였다.

| 주소 | 정체 |
|---|---|
| 깃허브 계정을 만든 주소 | 커밋에는 안 쓰이고 있었다 |
| **커밋에 박힌 주소** | **AI 도구 계정 이메일** — 깃허브와 무관 |
| 계정에 항상 연결되는 전용 주소 | 데스크탑만 이걸 쓰고 있었다 |

노트북은 윈도우 설정과 WSL 설정이 따로인데 **둘 다** 도구 계정 주소를 쓰고 있었다. 데스크탑만 전용 주소를 쓰고 있었고, 그래서 데스크탑에서 만든 커밋만 잔디에 찍혔다.

값이 비어 있지 않으니 문제로 보이지 않았다. 같은 실수를 이미 한 번 겪고 기록까지 남겨뒀는데도 또 밟았다. 그때 남긴 규칙은 "값이 있으면 손대지 않는다"였다. **그 규칙이 부족했다.** 값이 있는지가 아니라 **그 값이 계정에 연결되는 주소인지**를 봐야 했다.

해커톤에서 기여도가 평가에 들어간다면, 이건 코드를 아무리 써도 기록이 남지 않는다는 뜻이다.

## 내가 한 일, 도구가 한 일

| 도구가 한 것 | 내가 판단한 것 |
|---|---|
| 순환 로직과 콘텐츠를 짜고 문서 네 개를 갱신 | **파일만 추가하면 된다는 인계 메모를 코드로 확인하라고 했다** — 그게 틀려 있었다 |
| "검증 완료" 상태를 정리해 보고 | **세션 기록을 뒤져 반증했다** — 60회 호출에 2주차 응답 0회 |
| 두 세션이 소켓으로 서로 확인해 중복을 피함 | **한쪽을 읽기 전용으로 묶었다** — 안 묶으면 서로 덮어쓴다 |
| 90줄을 깔끔하게 고침 | **승인 모드를 되돌렸다** — 결과가 좋아도 안 보고 넘어가면 안 된다 |
| 커밋을 만듦 | **작성자가 계정에 연결됐는지 대조했다** — 세 개가 끊겨 있었다 |
| 배포 명령을 정리해 제시 | **배포는 미뤘다** — 사용자 두 명의 정체를 먼저 확인해야 한다 |

코드는 전부 도구가 썼고, 품질도 좋았다. **틀린 곳은 코드가 아니라 그 주변이었다.** 문서, 검증했다는 말, 계정 설정, 승인 모드.

## 남는 것

해커톤 전에 팀에 공유할 목록이 생겼다.

| 확인할 것 | 왜 |
|---|---|
| 넘길 정보를 저장소 안 문서에 적는가 | 대화는 기기를 안 넘는다 |
| 그 문서가 코드와 맞는지 확인했는가 | 문서는 그때의 믿음일 뿐이다 |
| "됐다"는 말의 **증거**를 봤는가 | 종료 코드도, 보고도 증거가 아니다 |
| 파일을 고치는 창이 하나인가 | 둘이면 서로 덮어쓴다 |
| 승인 모드가 꺼져 있는가 | 결과가 좋으면 켜진 걸 못 본다 |
| 기기마다 git 이메일이 계정에 등록된 주소인가 | 아니면 기여가 안 남는다 |

세 번째가 오늘 가장 서늘했다. 보고서에는 아무 거짓이 없었다 — "커밋·서버 정리·배포가 남았다"는 사실이었다. **다만 검증이 끝났다는 말은 아무도 하지 않았고, 나는 끝난 줄로 읽었다.** 안 적힌 것을 읽어낸 쪽이 나였다.

그래서 확인 방법을 바꿨다. "통과했나"라고 묻지 않고 **"응답 본문을 그대로 붙여라"**라고 요구했다. 요약은 사람이 읽기 좋게 다듬어지는 과정에서 빈칸이 메워진다.

코드는 [저장소](https://github.com/nike1137-svg/dementia-care)에 있다.

## 다음

워크플로는 굴러간다는 걸 확인했다. 그런데 정작 배포는 못 했다.

운영 서버에 사용자가 두 명 잡혀 있는데, **그게 내 기기와 테스트일 가능성이 크다.** 어제 운영에서 직접 세션을 완주한 기록이 있으니 최소 한 명은 나다. 남은 하나가 진짜 다른 사람이면 배포 판단이 달라진다.

발급 시각과 내 브라우저에 저장된 값을 대 봐야 안다. **아직 안 했다.** 다음은 그것부터다.

나흘 전에 "내 설명서는 나만 따라갈 수 있었다"고 적었고, 오늘은 "내가 나에게 넘긴 문서도 틀렸다"고 적는다. 두 번 같은 자리에 걸렸으니 다음엔 순서를 바꿔볼 생각이다. **문서를 먼저 쓰지 말고, 코드로 확인한 것만 문서에 적는 쪽으로.**

복약 앱의 자연어 읽기도 여전히 그 책상에 그대로 있다.
