[앞 글](/blog/posts/failed-but-printed-success/)을 이렇게 닫았다.

> 그리고 접었던 벤치마크를 그날 밤에 다시 폈다. 기준을 재고, 가설 하나를 세워 고치고, 같은 조건으로 다시 쟀다. **그 이야기는 다음 글에 적는다.**

낮에는 이렇게 계산했다. 10문항이 실제 공개 벤치마크 문제이고, 쉬운 쪽이 백트래킹 스도쿠 솔버다. 쓸 수 있는 모델은 노트북 CPU의 2.3B와 클라우드 T4의 4B. **어차피 0점이니 재봐야 "0에서 0"이라 비교가 안 된다.**

그래서 접었다. 접은 근거는 문서에 적어뒀다.

밤에 다시 폈다. 그리고 그 계산이 틀렸다는 걸 알았다.

## 1. 0점과 아무것도 못 한 것은 다른 얘기였다

돌려보니 **통과한 문항은 0개가 맞았다.** 그런데 채점 항목을 세어보니 달랐다.

```
공식 통과 : 0/10
검사 통과 : 28/304
```

각 문항은 검사 항목 여러 개로 채점된다. 논문 메타데이터 추출은 13개, LZ77 압축기는 85개다. **전부 통과해야 그 문항이 통과**다.

28개를 통과했다는 건 **일을 하긴 했다**는 뜻이다. 논문 문항은 13개 중 12개를 맞췄다. 하나만 더 갔으면 통과였다.

> **알고 가기 — 통과와 부분 점수**
> 자격증 시험에서 과목별 40점 이상, 평균 60점 이상 같은 기준을 생각하면 된다. **한 과목이라도 미달이면 불합격**이지만, 총점이 0점인 것과 59점인 것은 전혀 다른 상태다. 다음에 무엇을 고쳐야 할지도 다르다.

"어차피 0점"이라는 예상은 **합격/불합격만 본 것**이었다. 그 아래 숫자를 안 본 채로 측정을 건너뛰려 했다.

**예상이 측정을 대신할 수 없다.** 오늘 배운 것 중에 이게 제일 값이 나갔다.

## 2. 그런데 세 번은 측정 자체가 안 됐다

다시 펴고 나서 바로 결과가 나온 게 아니다. **처음 세 번은 데이터가 아예 안 남았다.**

첫 실행은 10문항이 47분 동안 다 돌았다. 그런데 결과 파일을 열어보니 이랬다.

```json
"agent_result": null,
"verifier_result": null,
"exception_info": { "exception_type": "TimeoutError" }
```

**10문항 중 9개가 이 상태였다.** 상태도 지표도 채점도 없었다.

원인은 시간 한도가 겹친 것이었다. 평가 도구는 문항당 300초를 준다. 그리고 내 하네스도 300초를 자기 한도로 잡고 있었다. **똑같은 숫자로 둘이 경합했고, 저쪽이 먼저 끊었다.**

평가 도구가 먼저 끊으면 내 하네스가 정리한 결과는 버려진다. 종료 이유도, 도구를 몇 번 썼는지도 안 남는다.

**재는 도구가 재려는 것보다 먼저 끝나버린 것이다.** 초시계가 주자보다 먼저 멈춘 셈이라, 몇 초에 들어왔는지 알 방법이 없다.

## 3. 255초로 줄였는데도 안 됐다

내 한도를 300초에서 255초로 낮췄다. 이제 내가 먼저 끝날 테니 될 거라고 봤다.

**1문항째부터 똑같았다.**

이유를 찾는 데 시간이 걸렸다. 내 루프는 이렇게 돈다.

```
시간 확인 → 모델 호출 → 도구 실행 → 시간 확인 → 모델 호출 → ...
```

**시간 확인은 모델 호출이 끝난 뒤에만 한다.** 예산이 20초 남았을 때 시작한 호출이 150초를 쓰면, 그 호출이 끝나는 시점은 이미 예산을 훌쩍 넘어 있다. 그 사이에 평가 도구가 300초를 세고 끊는다.

고친 방법은 이렇다. **모델을 부르기 직전에 남은 예산을 계산해서, 그만큼만 기다리게 했다.**

```python
remaining = self.limits.task_timeout_seconds - elapsed
self.provider.timeout_seconds = max(15.0, remaining - 3.0)
```

예산이 20초 남았으면 그 호출도 17초만 기다린다. **끊더라도 내가 끊어야 무엇에 걸렸는지 남길 수 있다.**

이건 개선 실험이 아니라 **계측 장비를 고친 것**이다. 그래서 이 수정이 적용된 상태에서 기준값을 새로 쟀다.

## 4. 고집부린 건 나였다

여기서 시간을 꽤 버렸다.

나는 로컬 CPU 모델을 고집했다. 이유는 "클라우드는 중간에 끊길 수 있고, 그러면 기준과 개선의 조건이 달라진다"였다. 실제로 그날 클라우드가 두 번 끊겼다.

그런데 로컬로는 **측정 자체가 안 됐다.** 모델 호출 한 번에 50초가 걸리니 300초 안에 세 단계밖에 못 밟고, 위의 타임아웃 경합까지 겹쳤다.

세 번째로 로컬을 다시 걸려고 할 때 이런 말을 들었다.

> 코랩으로 하면 되잖아. 너 왜 고집부려

맞는 말이었다. 클라우드로 옮기니 호출당 20초로 줄었고, 문항당 도구 호출이 8회에서 23회까지 기록됐다. **데이터가 나왔다.**

**"끊기지 않는 환경"을 지키느라 "측정이 되는 환경"을 놓쳤다.** 조건의 안정성을 따지는 건 측정이 될 때나 의미가 있는데, 나는 순서를 거꾸로 봤다.

## 5. 실패가 한 곳에 몰려 있었다

제대로 된 기준값이 나오자 실패 이유가 눈에 들어왔다.

| 종료 이유 | 문항 수 |
|---|---|
| 모델 서버 연결 오류 | 6 |
| 모델 서버 형식 오류 | 3 |
| 정상 종료 | 1 |

**10문항 중 9개가 모델 호출 오류로 끝났다.** 그 시점에 도구를 2~8회밖에 안 썼다. 한도는 160회였다.

논문 문항이 특히 아까웠다. 13개 중 12개를 통과한 상태에서 오류 하나로 끊겼다.

내 코드를 보니 이랬다.

```python
except ProviderError as error:
    return self._finish(TaskState.FAILED, ...)   # 즉시 끝
```

**재시도가 없었다.** 클라우드 터널을 거치는 구성에서 502나 일시적 연결 끊김은 다시 시도하면 성공할 수 있는데, 한 번 걸리면 그대로 끝이었다.

## 6. 바꾼 것은 한 줄짜리 설정 하나

가설을 이렇게 세웠다.

> 일시적인 모델 서버 오류에 재시도를 붙이면, 한 번의 오류로 작업이 끝나지 않는다.

그리고 **바꾸는 것을 하나로 제한했다.**

```
max_provider_retries:  0  →  2
```

코드 파일은 양쪽 실행에서 **똑같다.** 환경 변수 하나만 다르다. 이렇게 해야 결과 차이가 그 변경 때문인지 다른 것 때문인지 가릴 수 있다.

조건도 최대한 붙였다. **기준 실행이 끝나고 23초 뒤에 개선 실행을 걸었다.** 같은 서버, 같은 모델, 같은 문항 목록(해시까지 동일), 같은 예산.

안전장치도 넣었다.

- 인증 오류는 재시도 안 함 — 다시 물어도 같은 답이 온다
- 남은 예산이 부족하면 재시도 안 함 — 기다렸다 부를 시간이 없으면 그냥 끝낸다

## 7. 검사 통과가 두 배가 됐다

| | 기준 | 개선 |
|---|---|---|
| **공식 통과** | 0/10 | **0/10** |
| **검사 통과** | 28/304 | **61/304** |
| 파일을 만든 문항 | 4 | **10** |
| 서버 오류로 중단 | 9건 | **5건** |
| 쉬운 2문항 | 14/35 | **32/35** |
| 중간 4문항 | 8/68 | **23/68** |
| 어려운 4문항 | 6/201 | 6/201 |

**검사 통과가 2.2배가 됐다.** 논문 문항은 13/13으로 채점기가 통과 판정을 냈고, 데이터베이스 복구 문항은 0/30에서 22/30, 스도쿠는 2/22에서 19/22가 됐다.

**그런데 공식 점수는 0/10 그대로다.**

논문 문항이 왜 통과로 안 잡혔는지가 흥미롭다.

```
채점 결과 : 13/13 통과
에이전트  : 시간 초과로 미완료
공식 집계 : 통과 아님
```

**요구된 파일을 다 만들어 놓고, 다 했다고 알리기 전에 시간이 다 됐다.** 평가 도구는 미완료를 통과로 세지 않는다. 그 판정이 옳다고 본다.

## 8. 실패의 성격이 바뀌었다

숫자보다 이쪽이 더 말이 된다.

```
기준  : 서버 오류 9건 · 시간 초과 0건
개선  : 서버 오류 5건 · 시간 초과 4건
```

**시간 초과가 0건에서 4건으로 늘었다.** 언뜻 나빠 보이지만 그렇지 않다.

오류로 즉시 끝나던 것이 **계속 일하다가 시간이 다 되는 쪽으로 바뀐 것**이다. 그만큼 더 많은 검사를 통과했다. 병목이 "중단"에서 "시간 부족"으로 옮겨갔다.

**고치면 다음 병목이 드러난다.** 이게 개선 실험의 모양인 것 같다.

## 9. 나빠진 문항도 있다

한 문항은 오히려 떨어졌다.

| 문항 | 기준 → 개선 |
|---|---|
| 블록체인 손상 탐지 | **8/10 → 1/10** |

실행 기록을 열어봤다.

```
list_files app                         → 성공
read_file  blockchain_ledger.json      → 성공
read_file  blockchain_ledger.json      → 성공     같은 40KB 파일을 두 번
[오류] HTTP 400  "This model's maximum context length ..."
[재시도] 1회  2초 대기 → 같은 400
[재시도] 2회  4초 대기 → 같은 400
[종료] 56초, 파일 0건
```

**HTTP 400은 일시적 오류가 아니다.** "요청 자체가 잘못됐다"는 뜻이라 같은 요청을 다시 보내면 당연히 같은 답이 온다. 컨텍스트 길이를 넘겼는데 그대로 다시 보낸 것이다.

**내 분류가 틀렸다.** 나는 `provider_protocol`이라는 한 이름 아래 성격이 다른 오류를 묶어 두고, 전부 재시도 대상으로 삼았다. 재시도해야 할 것은 502·503·연결 끊김 같은 것이고, 4xx는 아니다.

그 문항에서 재시도는 회복에 기여하지 못했고 6초를 더 썼다.

**개선이 모든 경우에 듣지 않는다는 걸 이 한 문항이 보여줬다.** 좋아진 것만 적었으면 이걸 못 봤을 것이다.

## 10. 오늘 내가 판단한 일

**AI가 한 일**

- 벤치마크 연결부와 재시도 구현, 회귀 테스트 작성
- 측정이 안 된 원인 진단(타임아웃 경합)과 수정
- 결과 집계와 실험 보고서 초안

**내가 판단한 일**

- **접었던 것을 다시 편 것.** "어차피 0점"이라는 예상으로 측정을 건너뛰려 했다. 돌려보니 0점이 아니었다.
- **바꾸는 것을 하나로 제한한 것.** 재시도 말고도 고치고 싶은 게 여럿 보였는데, 두 개를 같이 바꾸면 어느 쪽 효과인지 알 수 없다.
- **기준을 다시 잰 것.** 첫 측정은 불안정한 서버에서 나온 값이었다. 그걸 기준으로 쓰면 개선 효과인지 서버 상태 차이인지 구분이 안 된다.
- **나빠진 문항을 표에 넣은 것.** 빼면 그래프가 예뻐진다. 그런데 그러면 재시도의 한계를 못 본다.
- **공식 점수를 0/10으로 적은 것.** 검사 통과 61개를 앞세우고 싶었지만, 통과 문항은 0개가 맞다.

**틀린 자리도 남긴다.**

**로컬 환경을 고집하다 시간을 버렸다.** "안 끊기니까 조건이 안정적"이라는 논리에 갇혀서, 정작 **측정이 안 되고 있다**는 사실을 늦게 인정했다. 세 번을 같은 방식으로 시도했다. 지적을 받고 나서야 옮겼다.

[자를 세 번 갈아 끼웠다](/blog/posts/changed-the-ruler-three-times/)에서 비슷한 걸 겪었다. 그때는 판정 기준을 세 번 고쳤고, 이번엔 **측정 환경을 세 번 갈아 끼웠다.** 같은 자리에서 또 걸린 셈이다.

## 11. 남은 질문

**한 번 돌린 결과를 얼마나 믿을 수 있나.**

문항당 1회씩만 돌렸다. 평가 도구 안내에는 3회 반복을 권한다. 그러니까 블록체인 문항이 나빠진 게 재시도 때문인지, 모델이 그날 마침 파일을 두 번 읽어서인지 **이 데이터로는 가릴 수 없다.**

검사 통과가 28에서 61로 는 것도 마찬가지다. 방향은 뚜렷하지만 **한 번은 한 번이다.**

측정이 되게 만드는 데 하루를 썼는데, 그 측정을 믿을 만하게 만들려면 또 반복이 필요하다. **재는 것과 믿을 만하게 재는 것 사이에 이만큼 거리가 있는 줄 몰랐다.**

다음은 **재시도 대상을 오류 종류로 좁혀서 다시 재는 일**이다. 4xx는 재시도해도 소용없다는 게 이번 기록에 남았으니, 그것부터 걷어내고 같은 조건으로 측정한다. 큰 점수 상승은 기대하지 않는다. 헛되이 기다리는 시간을 없애는 것이 목적이다.
