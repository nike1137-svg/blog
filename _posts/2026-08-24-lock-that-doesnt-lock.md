두 가지를 동시에 하려고 시작한 작업이다.

하나는 GitHub 계정 두 개로 실무에서 마주치는 상황을 **일부러 만들어보는 것**이다. 혼자 저장소를 쓸 때는 만날 일이 없는 일들 — 권한이 어디까지 열려 있는지, 두 사람이 같은 파일을 건드리면 어떻게 되는지, 잘못 올린 걸 어떻게 되돌리는지 — 을 실제로 겪어보려는 것. 해커톤에서 팀으로 일해보니 정작 어려운 건 코드가 아니라 이런 상황들이었다.

다른 하나는 맥미니를 로컬 추론 노드로 세우는 실제 프로젝트다. 연습만 하고 버릴 저장소가 아니라, 계속 쓸 프로젝트를 그 실습의 무대로 삼았다.

지난 글 마지막에 이렇게 적었다. "다음엔 이 자물쇠가 실제로 걸리는지 직접 눌러서 확인해볼 것이다." 오늘 그 문을 밀어봤는데, 열렸다.

## 1. 자물쇠는 걸었는데 잠기지 않았다

새 저장소를 만들고 main 브랜치에 보호 규칙을 걸었다. PR 없이는 머지 못 하게, 승인 1명은 반드시 받게. 설정을 저장하니 규칙 목록에 `main`이 뜨긴 했다. 그런데 그 옆에 작은 글씨로 **Not enforced**라고 적혀 있었다.

> **알고 가기** — Not enforced는 "규칙은 만들어졌지만 실제로는 강제되지 않는다"는 뜻이다. 문에 자물쇠를 걸어뒀는데 고리가 안 채워진 상태와 같다. 보기엔 잠겨 있다.

이유는 GitHub 무료 플랜에서 Private 저장소에는 브랜치 보호가 적용되지 않기 때문이었다. Public으로 열거나 유료 플랜이어야 작동한다. 지난 글에서 "규칙 문서에 적힌 문장을 실제 권한 설정으로 옮겼다"고 썼는데, 옮기긴 옮겼고 **작동은 안 하고 있었다.**

## 2. 빈 저장소에는 걸 자물쇠가 없다

그 전에 한 번 더 막혔다. 저장소를 만들 때 README 생성 체크를 안 하고 만들었더니, 브랜치 설정 화면에 "You don't have any branches"만 떠 있었다.

커밋이 하나도 없으면 브랜치도 없고, 브랜치가 없으면 보호할 대상 자체가 없다. README 하나를 만들어 첫 커밋을 넣으니 그제야 `main`이 생기고 설정 화면이 열렸다. 문을 달기 전에 벽부터 세워야 한다는, 당연한데 순서를 밟아보기 전엔 몰랐던 것.

## 3. 그래서 어떻게 했나

선택지는 세 개였다. Public으로 열어서 규칙을 살리거나, 유료로 올리거나, 규칙 없이 진행하거나.

이 저장소는 당분간 Private로 둬야 할 이유가 있어서 첫 번째는 제외했고, 비용을 쓸 단계는 아니라 두 번째도 접었다. 남은 건 세 번째 — **규칙을 "지키기로 한 약속"으로만 두고 가는 것.**

처음엔 반쪽짜리 같았는데, 생각해보니 이번 실습의 목적은 강제 장치를 만드는 게 아니라 브랜치 → PR → 리뷰 → 머지 흐름을 몸에 익히는 쪽이었다. 강제가 없어도 그 순서를 지키면 습관은 똑같이 든다. 나중에 Public으로 전환하는 시점에 규칙은 알아서 살아난다.

## 4. 새 저장소를 세웠다

여기까지가 확인 작업이었고, 그 위에 실제 프로젝트를 올렸다. 맥미니를 로컬 추론 노드로 쓰는 작업 저장소다.

구조는 이렇게 잡았다.

| 역할 | 하는 일 |
|---|---|
| 저장소 주인 | 최종 검토와 머지 |
| 협업자 | 브랜치 작업과 PR 생성 |

두 계정이 각자 다른 SSH 키로 붙고, 저장소 폴더마다 커밋에 찍힐 이름을 따로 지정했다. 지난번에 겪은 함정 — 전역 설정이 한쪽 계정으로 잡혀 있어 엉뚱한 이름으로 커밋되던 것 — 을 이번엔 clone 직후에 미리 잡아뒀다. 한 번 당해본 것은 다음엔 순서에 넣게 된다.

## 5. 공개할 때를 미리 정해두기

이 저장소는 언젠가 공개하고 이 블로그에 연결할 생각인데, 그때 커밋 기록과 협업자 목록에 두 계정의 관계가 그대로 드러난다. 나중에 지우려면 히스토리를 다시 쓰거나 PR을 따로 정리해야 하는데, 둘 다 손이 많이 가고 빠뜨리기 쉽다.

그래서 방향을 먼저 정했다. **연습용 히스토리와 공개용 최종본을 처음부터 분리한다.** 지금 저장소는 Private로 끝까지 두고, 공개 시점이 오면 완성된 코드만 새 저장소에 단독 커밋으로 옮긴다. 예전에 블로그 저장소를 정리할 때 썼던 것과 같은 방식이다.

사후에 지우는 것보다 애초에 섞지 않는 쪽이 실수가 적다.

## AI가 한 일 vs 내가 판단한 일

| AI가 한 일 | 내가 판단·검토한 일 |
|---|---|
| 설정 위치 안내, 명령어 작성 | 규칙이 실제로 걸렸는지 화면으로 확인 |
| 선택지 3개 정리 | Private 유지 + 규칙 없이 진행을 택함 |
| 공개 시 노출 위험 지적 | 새 저장소로 분리하는 방향 결정 |

오늘 AI가 한 번 틀렸다. 규칙이 Not enforced인 걸 보기 전에 "승인 필수만으로도 충분하다"고 했는데, 화면을 보니 승인 규칙 자체가 작동하지 않는 상태였다. 화면을 직접 확인하지 않았으면 그대로 넘어갔을 것이다. 지난 블로그 정리 때 얻은 교훈 — **추측 말고 직접 확인** — 이 여기서도 그대로 통했다.

다음은 이 저장소에 요구사항 문서부터 올리는 일이다. 코드보다 문서가 먼저인 구조를, 이번엔 내가 세워보려 한다.
