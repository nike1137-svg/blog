어제 [가장 싼 것이 가장 크게 이겼다](/blog/posts/cheapest-fix-won-biggest/)를 "프롬프트 몇 줄이 30분 학습을 이겼다"로 닫았다. 그러면 반대쪽은 어떨까 — **학습 데이터를 크게 늘리면 파인튜닝이 역전할까.** 오늘 그걸 밀어봤다. 결론부터 쓰면 역전은 없었고, 대신 지표에 대해 또 하나 배웠다.

## 1. 데이터 확보 — 156GB에서 4.5GB만

AI Hub에서 라벨링 데이터만 골라 받았다. 음성 145GB를 제외하니 실제 내려받은 건 4.49GB(zip 18개)였다. 어제 확인한 대로 텍스트 변환 학습에 음성은 한 개도 안 쓰인다.

압축을 아예 풀지 않고 Python `zipfile`로 직접 읽어 쌍만 뽑았다. 디스크 10GB를 아꼈다. 결과는 **사투리-표준어 쌍 364,257개**.

지역 비중이 어제와 정반대였다. 전라 53%, 충청 34%, 제주 12% — 어제 샘플에서는 제주가 41%였다. **샘플의 분포를 전체 분포로 믿으면 안 된다는 게 여기서 다시 확인됐다.**

## 2. 발화 유형별로 성격이 완전히 달랐다

데이터가 세 유형으로 나뉘는데, 사투리 비율(표준어와 실제로 다른 문장의 비율)이 크게 달랐다.

| 유형 | 사투리 비율 | 성격 |
|---|---|---|
| read (따라말하기) | 95~99% | 사투리 문장을 읽으라고 시킨 것 — 인위적 |
| answer (질문답변) | 32~80% | 자유 발화 |
| dialog (2인 대화) | 39~85% | 실제 대화 |

read는 사투리 밀도가 가장 높지만 **실제 대화가 아니다.** 목표가 어르신의 자연스러운 말을 알아듣는 것이라 read는 제외했다. answer와 dialog에서 지역별로 균등하게 1,666쌍씩 뽑아 train 4,998개를 만들었다.

test 95개는 어제 것을 그대로 뒀다. **평가 기준을 고정해야 비교가 성립한다.** 새로 뽑은 데이터에 test 문장이 섞여 들어갈 수 있어서 명시적으로 걸러냈다.

## 3. 재학습 — 2시간 20분

train을 763개에서 4,998개로 늘렸다(6.5배). 2,500 iter, batch 2, num-layers 16, grad-checkpoint. Peak memory는 12.70GB로 24GB의 절반을 조금 넘었다. 어제와 마찬가지로 메모리는 병목이 아니었다.

512토큰을 넘는 문장이 잘렸다(837토큰, 1063토큰짜리가 있었다). 자연 발화라 문장이 길다.

## 4. 세 번째 역설 — Val loss가 낮은 쪽이 BLEU는 더 낮았다

학습 중 Val loss는 이렇게 움직였다.

```
Iter 1: 4.465 → 500: 0.655 → 1000: 0.650 → 1500: 0.657 → 2000: 0.563 → 2500: 0.738
```

2000에서 최저(0.563)를 찍고 2500에서 올랐다(0.738). Val loss가 다시 오르는 건 과적합 신호로 읽힌다. 그래서 2000스텝 저장분이 더 좋을 거라 예상하고, 두 어댑터를 다 재봤다.

| 어댑터 | Val loss | RAG BLEU |
|---|---|---|
| 2000스텝 | 0.563 (좋음) | 77.55 |
| 2500스텝 | 0.738 (나쁨) | **79.01** |

**정반대였다.** Val loss만 보고 골랐으면 더 나쁜 모델을 선택할 뻔했다.

두 지표가 재는 게 다르기 때문이다. Val loss는 "다음 글자를 얼마나 잘 맞추는가"고, BLEU는 "완성된 문장이 정답과 얼마나 겹치는가"다. 학습 중 지표가 좋아지는 것과 최종 산출물이 좋아지는 것은 별개일 수 있다. 어제 copy baseline에서 배운 것과 같은 교훈이 다른 형태로 반복됐다 — **어떤 자로 재는지 확인하지 않으면 잘못된 쪽을 고른다.**

## 5. 결론 — 데이터를 늘려도 개선이 없었다

| 학습 | 데이터 | 시간 | RAG BLEU |
|---|---|---|---|
| 어제 | 763개 | 30분 | **79.39** |
| 오늘 | 4,998개 | 2시간 20분 | 79.01 |

차이는 −0.38. 오차 범위다. 데이터를 6.5배 늘리고 학습을 4.7배 오래 돌렸는데 개선이 없었다. **병목은 데이터량이 아니었다는 뜻이다.**

원인으로 짚이는 건 세 가지다 — read 데이터를 뺀 것, 자연 발화의 낮은 사투리 밀도, 문장 잘림. 다만 어느 것이 결정적인지는 **확인하지 않았다.** 추정으로 남겨둔다.

## 6. 숫자만 보지 않고 직접 물어봤다

BLEU가 비슷하다고 넘기지 않고, 학습 데이터에 있던 문장을 직접 넣어 무엇을 배웠는지 확인했다.

**배운 것** — 어미와 조사 변환은 정확했다. "메누리→며느리", "메누리덜→며느리들", "인저→인제"를 맞혔고 "참어 참어→참아 참아" 같은 미세한 변환까지 잡았다. 그리고 표준어 문장은 한 글자도 건드리지 않았다. 어제 프롬프트 v2에 넣은 "방언이 아닌 부분은 원문 그대로" 조건이 학습에도 반영된 것으로 보인다.

**못 배운 것** — 제주 어휘 "무장→무작정"을 "너무"로 오역했다. 어제 못 맞힌 "조선솔→조선부추"도 여전히 실패했다.

정리하면 이렇다. **어미 변환은 규칙이라 학습되고, 어휘는 지식이라 5천 개로는 안 들어갔다.** 그리고 어제 확인한 대로 어휘 문제는 RAG로 잡힌다 — 검색해서 예시를 붙여주면 맞힌다. 파인튜닝과 RAG가 보완재라는 어제 결론이 여기서 더 선명해졌다.

## 7. 방향 전환 — 온담이가 무엇으로 도는지 확인했다

파인튜닝이 한계에 닿아서, 원래 목적인 온담이 로컬 이관으로 돌아왔다. 그런데 여기서 내 시스템에 대한 오해가 드러났다.

OpenClaw에 `dodami` 에이전트가 있고 LINE 채널도 ON으로 잡혀 있었다. 그래서 온담이가 OpenClaw로 돈다고 생각하기 쉬웠다. 확인해보니 달랐다.

- 세션 파일 0개
- `sessions.json` 2바이트(비어 있음)
- 유일한 세션은 7월 3일에 삭제 처리됨
- **온담이를 실제로 써본 직후에도 OpenClaw 쪽에 새 파일이 생기지 않았다**

**온담이는 처음부터 n8n 워크플로우였다.** 4월 기록에도 "도담이의 LINE 기능은 n8n 기반 stateless, 자비스의 텔레그램은 완전한 OpenClaw 에이전트"로 구분돼 있었다. 5월에 도담이에서 온담이로 이름을 바꿀 때 OpenClaw 설정의 표시 이름만 고치고 내부 ID(`dodami`)는 그대로 뒀는데, 그 흔적이 남아 헷갈렸던 것이다.

**설정 파일에 있다고 도는 게 아니다.** 파일 수정 시각과 세션 개수가 설정보다 정직했다.

## 8. 로컬 모델로 온담이가 가능한지 — 두 가지를 쟀다

### 대화 품질

실사용 중인 Gemini 2.5 Flash의 응답과 비교했다. 질문은 "카카오톡이 뭐야".

첫 시도에서 `gemma4:12b`가 두 가지를 틀렸다. "어르신께 이렇게 말씀드려보세요"라며 제3자를 코칭했고, 마크다운 별표(`**`)를 뱉었다. LINE에서는 별표가 그대로 보인다.

둘 다 프롬프트 문제였다. "당신은 어르신의 말동무 온담이입니다. 어르신과 직접 대화합니다. 마크다운 기호를 쓰지 마세요"로 고치니 Gemini와 구분이 안 되는 답이 나왔다. 오히려 "동네 사랑방처럼" 같은 표현은 더 나았다. **여기서도 답은 프롬프트였다** — 어제와 같은 패턴이다.

### 도구 호출

에이전트로 만들려면 LLM이 스스로 어떤 도구를 부를지 판단해야 한다. 도구 3개(시각/날씨/버스)를 주고 6가지를 물었다.

| 질문 | 결과 | 시간 |
|---|---|---|
| 지금 몇 시야? | `get_time` | 4.1초 |
| 서울 날씨 어때? | `get_weather(city=서울)` | 3.1초 |
| 강남역 버스 언제 와? | `get_bus(station=강남역)` | 3.3초 |
| 안녕하세요 | 도구 안 부름 (대화로 응답) | 7.8초 |
| 요즘 무릎이 좀 아파 | 도구 안 부름 (공감 응답) | 20.7초 |
| 내일 비 오나? | 도구 안 부름, 지역을 되물음 | 5.5초 |

도구 이름과 인자를 정확히 뽑았다. 일상 대화에 도구를 부르지 않는 것도 됐다 — 이게 안 되면 챗봇이 이상해진다.

마지막 건은 표면상 실패지만 실제로는 옳은 행동이다. `city`가 필수인데 사용자가 지역을 말하지 않았으니 임의로 채우지 않고 되물었다. **없는 정보를 지어내는 것보다 낫다.** 실질 6/6이다.

**남은 문제는 속도다.** 공감 대화에 20.7초가 걸렸다. 어르신이 20초를 기다리면 고장난 줄 안다. 도구 호출은 3~4초로 빠른데(짧은 JSON만 출력하니), 긴 문장을 만들 때 느려진다.

## 9. 검증 파일은 즉시 지웠다

테스트용으로 만든 스크립트는 결과를 얻은 뒤 폴더째 지우고 삭제됐는지 확인했다. 검증용 파일을 시스템에 남기지 않는 게 내 원칙이다.

## AI가 한 일, 내가 판단한 일

| AI가 한 일 | 내가 판단한 일 |
|---|---|
| 스크립트 작성, 옵션 설명, 결과 표 정리, 원인 추정 | 156GB를 다 받지 않고 라벨링만 골라 받기로 한 것 (4.5GB) |
| — | read 데이터를 제외한 것 — 사투리 밀도는 높지만 실제 대화가 아니므로 |
| — | test 95개를 고정해 어제와 비교 가능하게 유지한 것 |
| — | 숫자만 보지 않고 직접 문장을 넣어 확인한 것 — 어미는 배우고 어휘는 못 배웠다는 걸 여기서 발견 |
| 온담이 구조를 설명함 | 그 설명을 믿지 않고 **"실제로 써보고 파일이 생기는지"** 확인하자고 한 것 — 이 방법이 결론을 냈다 |
| 블로그를 읽지도 않고 "들어가 있습니다"라고 단정함 | 그걸 지적한 것. 확인한 것과 추정한 것을 구분하게 만드는 건 계속 내 몫이다 |
| — | 검증 파일을 남기지 않는 원칙을 지키게 한 것 |

오늘 배운 건 두 가지다. 하나, 데이터를 늘리는 건 병목이 아닐 때는 시간만 쓴다. 6.5배와 2시간 20분을 넣고 얻은 게 −0.38이었다. 둘, 지표는 어제도 오늘도 엇갈렸다 — copy baseline이 없으면 개선을 착각하고, Val loss만 보면 더 나쁜 모델을 고른다. **무엇을 재는 자인지 확인하지 않으면 숫자가 방향을 잘못 알려준다.**

용어를 따로 정리한 건 [오늘의 용어 정리 — 하네스·MCP·트랜스포머·서빙 엔진](/blog/posts/terms-harness-to-mcp/)에 두었다.

다음은 응답 길이를 제한해 20.7초 문제를 잡는 것부터다. 그다음 Ollama를 Tailscale 주소로 열어 리눅스에서 호출하게 하고, 재부팅 후 자동 시작을 확인한다. 다만 긴급 감지는 AI 판단에 맡기지 않고 키워드 규칙으로 남길 생각이다 — 오탐이면 사용자가 곤란해지고 미탐이면 안전 문제라, 확실한 쪽을 쓴다.
