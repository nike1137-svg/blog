오늘부터 프롬프트 엔지니어링 마스터 모듈이 시작됐다. 첫 실습은 단순했다. 같은 질문을 세 번 호출하는데, 첫 번째는 system 지시를 정중한 톤으로, 두 번째는 기술 문서 톤으로, 세 번째는 앞선 대화 이력을 추가해서 보낸다. 그리고 세 개의 SDK — Claude Agent SDK, LangChain+Gemini, Ollama — 로 각각 돌려서 응답이 어떻게 갈리는지 원문으로 남기라는 것이었다.

간단해 보였다. 교재에 있는 코드를 그대로 옮기기만 하면 되는 줄 알았다. 그런데 셋 다 멈췄다. 그것도 각자 완전히 다른 이유로.

> 관련 개념: [우리가 쓰던 도구가 사실 '에이전트'였던 날](/blog/posts/tool-was-an-agent/)에서 다룬 MCP와 스킬이, 오늘은 실습 코드 안으로 원치 않게 흘러들어오는 쪽으로 다시 나타났다.
{: .prompt-info }

## 1. Claude Agent SDK — 내가 보낸 입력과 모델이 받은 입력이 달랐다

내가 준 system 지시는 딱 한 줄이었다.

```
고객 문의에 정중하게 답한다
```

그런데 응답이 이렇게 시작했다.

> 안녕하세요, **마커스님**. 문의 주셔서 감사합니다.

지시 어디에도 호칭을 정한 적이 없다. 원문 파일을 열어보니 이유가 있었다.

```
cache_creation_input_tokens: 3782
```

내가 보낸 입력은 2토큰짜리 질문 하나였는데, 실제로 모델에 실린 건 3,782토큰이었다. `setting_sources` 라는 옵션의 기본값이 `None` 인데, 이게 "아무것도 안 읽는다"가 아니라 "개인 설정 파일, 로컬 스킬, 프로젝트 설정을 전부 읽는다"는 뜻이었다. 평소 쓰던 CLAUDE.md와 블로그 스킬 25개가 통째로 system 자리에 끼어 들어간 것이다.

두 번째 문제는 더 골치 아팠다. 세 번째 호출(이력을 추가한 것)이 `error_max_turns` 로 죽었다. 원문을 뒤져보니 모델이 실제로 Gmail 검색 도구를 호출하려 한 흔적이 있었다.

```
ToolUseBlock(name='mcp__claude_ai_Gmail__search_threads')
cache_read_input_tokens: 27957
```

배송일을 묻는 대화에 Gmail이 왜 나오나 싶었는데, 앞서 흘러들어온 개인 설정 때문에 모델이 스스로를 "메일함을 뒤질 수 있는 에이전트"로 인식한 것이었다. `max_turns=1` 로 걸어둔 제한에 도구 호출이 걸려서 그 자리에서 멈췄다.

해결은 옵션 세 줄을 더 넣는 것이었다.

```python
setting_sources=[],
mcp_servers={},
strict_mcp_config=True,
```

이걸 넣고서야 세 번의 호출이 전부 성공했다. 그런데 그러고도 응답에 내 이메일 주소가 남아 있었다. 파일도 커넥터도 다 막았는데, 구독 로그인 자체가 계정 정보를 프롬프트에 실어 보내는 것 같았다. 옵션으로는 더 막을 수가 없었다.

## 2. LangChain + Gemini — 서버 사정, 한도 사정, 그리고 내 실수

여기서는 처음엔 서버가 문제였다.

```
503 UNAVAILABLE. This model is currently experiencing high demand.
```

`gemini-3.7-flash` 가 붐볐다. 세 번 다시 돌려도 계속 503이었다. 교재 코드에는 `try/except` 가 없어서, 세 번의 호출 중 하나만 실패해도 나머지는 시작도 못 하고 스크립트가 끝났다.

재시도 로직을 넣어서 다시 돌렸는데, 이번엔 오류가 바뀌었다.

```
429 RESOURCE_EXHAUSTED
quotaValue: 20
```

`gemini-3.7-flash` 의 무료 등급 하루 호출 한도가 **20회**였다. 503과 429를 같은 재시도 로직으로 묶어서 처리한 게 실수였다. 503은 잠깐 기다리면 풀리지만, 429는 기다려도 한도가 돌아오지 않는다. 재시도를 반복하다가 남은 한도를 스스로 다 태워버렸다.

모델을 바꾸려고 `gemini-2.5-flash` 로 시도했더니 이번엔 다른 오류가 나왔다.

```
404 NOT_FOUND. This model is no longer available to new users.
```

신규 사용자에게는 제공이 끊긴 모델이었다. 오류 메시지가 알려준 `gemini-3.6-flash` 로 바꾸고서야 세 번의 호출이 다 성공했다.

성공한 뒤에도 한 가지가 더 남아 있었다. 저장한 파일을 열어보니 응답 본문이 아니라 이런 게 들어 있었다.

```
[{'type': 'text', 'text': '안녕하세요...', 'extras': {'signature': 'Ep8SCpwSAR...
```

`answer.content` 를 그대로 문자열로 바꿔서 저장하면, 내용 조각 리스트가 그대로 찍히면서 서명 문자열까지 파일에 들어갔다. 지금 쓰는 langchain-core 버전에서는 응답 텍스트만 뽑는 `answer.text` 를 따로 써야 했다.

## 3. Ollama — 5분 동안 생각만 하고 아무 말도 안 한 호출

세 번째 SDK는 로컬에서 돌아가는 `qwen3.5:2b` 였다. 인증도 없고 요금도 없어서 제일 마음이 편했는데, 세 번째 호출(이력을 추가한 것)에서 5분 넘게 걸리더니 파일이 0바이트로 끝났다.

`ollama show qwen3.5:2b` 로 모델 정보를 확인해보니 답이 있었다.

```
Capabilities
    completion
    vision
    tools
    thinking
```

이 모델은 답을 내기 전에 사고 과정을 따로 생성하는 thinking 모델이었다. 그 사고 과정이 `message.content` 가 아니라 다른 자리에 담기는데, 교재 코드는 `content` 만 저장하니 5분을 사고만 하다가 빈 파일로 끝난 것이었다.

`think=False` 옵션 하나로 이 문제가 풀렸다. 그리고 그 한 줄이 바꾼 게 생각보다 컸다.

```
사고 켜짐: 12분 41초 (3호출)
사고 끔:     56초 (3호출)
```

전체 시간의 93%가 사고 단계였다. 그런데 빨라졌다고 안심할 상황이 아니었다. 세 번째 호출의 응답을 열어보니 이렇게 시작했다.

> 죄송합니다만, 현재에는 **주식 종목**을 확인할 수 있는 기능이 없습니다. (…) 반드시 해당 **증권사** 또는 관련 금융 서비스 앱/웹사이트에서 확인하셔야 합니다.

배송일을 묻는 대화였는데, 이력에 있던 "주문번호"라는 단어를 증권 주문으로 읽은 것 같았다. 게다가 응답 곳곳에 `运费`, `发货` 같은 중국어가 섞여 나왔다. 작은 양자화 모델이 원래 학습 언어의 흔적을 그대로 드러낸 것이다.

## 4. 셋을 나란히 놓고 보니 — 이력을 넣는 방법과 모델이 그걸 쓰는 능력은 별개였다

이번 실습에서 세 SDK가 앞선 대화 이력을 넣는 방식이 전부 달랐다.

- Claude Agent SDK는 assistant 이력을 배열로 넣는 방법이 아예 없어서, 이력을 통째로 글로 풀어 user 메시지 안에 적어 보냈다.
- LangChain은 `AIMessage` 객체로 이력을 표현할 수 있었다.
- Ollama는 `{"role": "assistant", ...}` 딕셔너리로, 세 방식 중 가장 정석에 가까웠다.

그런데 결과는 방식의 정교함과 반대로 갔다. 가장 우회적으로 이력을 넣은 Claude가 맥락을 정확히 이어받았고, 가장 정석대로 넣은 Ollama가 대화 주제 자체를 놓쳤다. 이력을 어떤 형태로 넣었는지와, 모델이 그 이력을 실제로 이해하는지는 완전히 다른 문제였다.

배송일에 대한 답변도 셋이 갈렸다. Claude는 정보가 없다고 명확히 밝혔고, Gemini는 괄호로 조건을 달아 "일반적으로는"이라고 에둘러 말했고, Ollama는 표까지 만들어서 없는 숫자를 채워 넣었다. 물어보지 않은 것에 답을 지어내는 정도가 모델마다 확실히 달랐다.

## 5. 검증 — 뭘 보고 됐다고 판단했나

화면에 오류 없이 끝났다고 넘어가지 않았다. Claude Agent SDK의 경우 첫 번째 호출은 오류 표시(`is_error`) 없이 성공으로 끝났는데도, 원문을 열어보니 이미 3,782토큰짜리 개인 설정이 섞여 있었다. 오류가 없다는 것과 의도대로 됐다는 것은 다른 이야기였다.

그래서 실패했던 버전들을 지우지 않고 폴더로 남겼다. 오염된 상태(v1), 절반만 막힌 상태(v2), 다 막은 상태(v3)를 나란히 두니 어느 옵션이 무엇을 막았는지 숫자로 비교가 됐다. 그리고 로컬 실행은 `time` 명령으로 실제 걸린 시간을 재서, "느리다"는 인상이 아니라 12분 41초라는 숫자로 남겼다.

## AI가 한 일, 내가 판단한 일

원문 파일에서 오류 원인을 찾고, 옵션을 하나씩 추가해가며 재현하는 과정은 AI와 함께 진행했다. 하지만 어느 실패를 계속 붙잡고 원인을 팔지, 어느 시점에서 다음 SDK로 넘어갈지는 내가 정했다. 그리고 옵션을 세 겹으로 막았는데도 이메일 주소가 남았을 때 "이건 지금 실습 범위를 넘어간다"고 선을 그은 것도 내 판단이었다.

같은 실습 코드가 세 번 다 다르게 멈췄다는 게 오늘의 요지다. 다음 실습에서는 이 세 SDK 중 하나로 실제 대화형 흐름을 좀 더 길게 이어가 볼 생각이다.
