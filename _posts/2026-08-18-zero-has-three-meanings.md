이틀 전 글 끝에 "다음은 복약 알림 앱"이라고 적어뒀는데 그쪽으로 못 갔다. 기업연계 해커톤이 시작됐다.

3인 팀이고 나는 **논문 데이터를 모아 오는 부분**을 맡았다. 과제 내용 자체는 대외비라 적을 수 없다. 대신 내가 코드로 부딪힌 것만 쓴다. 공개 API 하나와, 내 판단 몇 개다.

## 1. 0건에는 세 가지 뜻이 있다

이 도구의 목적은 "놓치지 않는 것"이다. 그런데 조회 결과가 **0건**으로 나왔을 때, 화면만 봐서는 무슨 일이 있었는지 알 수가 없다.

- 정말 새 논문이 없어서 0건인가
- 조회할 식별자가 없어서 아예 물어보지도 못한 건가
- 물어봤는데 네트워크가 끊겨서 0건인가

셋이 화면에서 같아 보이면, 사용자는 **"확인했다"고 믿는다.** 그리고 그게 틀렸을 때는 도구가 아예 없는 것보다 나쁘다. 없으면 직접 찾아봤을 텐데, 있으면 안 찾는다.

창고에 재고를 물었더니 "없습니다"라는 답이 왔다고 하자. 직원이 실제로 창고에 가서 본 건지, 창고 열쇠가 없어서 못 들어간 건지, 애초에 창고 번호를 잘못 들은 건지 — 답은 똑같이 "없습니다"다. 셋을 구분해서 말해주지 않으면 그 답은 쓸모가 없다.

그래서 조회 기록 하나하나에 **상태**를 남기기로 했다.

```
ok       정상 조회. 0건이면 진짜 '신규 없음'
no_id    식별자가 없어 조회 자체를 못 함 → '확인 불가'
failed   호출은 했는데 실패 → '조회 실패'
```

## 2. 틀린 질문에도 그럴듯하게 답하는 API

내가 쓰는 소스는 Europe PMC다. 논문 검색 공개 API고 키가 필요 없다. 저자 식별자(ORCID)로 조회한다.

붙이기 전에 일부러 이상한 질문을 던져 봤다. 결과가 예상과 달랐다.

```
존재하지 않는 ID  0000-0000-0000-0000  →  31건
문법이 깨진 질의   AUTHORID:(((         →   6건
ID 칸을 비움      AUTHORID:            →  224건
유효한 ID 앞뒤에 공백 하나              →   0건
```

전부 **HTTP 200**이다. 오류가 아니다. 서버는 "잘 처리했습니다" 하고 숫자를 돌려준다.

손님이 뭘 물어도 "네, 여기 있습니다" 하며 아무거나 꺼내 주는 가게 같다. 물건을 안 준 것도 아니고, 화도 안 냈다. 그래서 더 위험하다. **받은 쪽은 자기가 뭘 받았는지 모른다.**

특히 마지막 줄이 무섭다. 유효한 ID인데 앞뒤에 공백이 하나 붙으면 조용히 0건이 된다. 엑셀에서 복사하면 실제로 이렇게 섞인다. 화면에는 "신규 없음"으로 뜬다.

그래서 방어를 두 겹으로 뒀다.

1. **입력 검증** — ID를 정규화하고 형식을 확인한다. 통과 못 하면 **API를 호출하지 않는다.** 빈 값으로 물어보면 224건의 남의 논문이 들어오니까
2. **응답 검증** — 받아온 논문의 저자 목록에 내가 물어본 ID가 실제로 있는지 코드로 확인한다. 없으면 버린다

그리고 버린 개수를 화면까지 올린다. `받아온 수 - 채택한 수`가 곧 **「조용한 실패 탐지량」**이다. 0이 아니면 뭔가 잘못됐다는 뜻이다.

> **알고 가기** — HTTP 200은 "요청이 문법적으로 처리됐다"는 뜻이지 "내가 원한 걸 받았다"는 뜻이 아니다. 상태 코드만 보고 성공으로 넘기면, 틀린 데이터가 성공으로 위장해서 들어온다.

## 3. 규격이 27분 전에 바뀌어 있었다

3인이 동시에 코드를 짜니, 서로 주고받을 **데이터 모양**을 먼저 맞춰야 했다. 팀에서 공용 파일 하나에 그 규격을 정해뒀다. 이 파일은 마음대로 못 고친다. 바꾸려면 팀 합의를 거친다.

그런데 내가 만든 게 옛 규격에 맞춰져 있었다.

```
17:07  팀 저장소에 어떤 변경이 반영됨   ← 내 폴더가 여기서 멈춰 있었음
17:13  내가 코드 작성 시작
17:21  git pull                       ← 여기까지만 받아옴
17:36  코드 작성 완료
─────────────────────────────────
17:48  ★ 새 규격이 반영됨              ← pull 27분 뒤
```

**깃은 자동으로 안 받아온다.** 당연한 얘긴데, 받아온 시각과 바뀐 시각이 27분 차이라는 걸 알아채기가 어려웠다. 내 화면에는 아무 표시도 없다.

도면을 받아서 부품을 깎았는데, 깎는 사이에 도면이 개정된 것과 같다. 부품은 잘 만들었고 치수도 정확한데, 지금 도면이 아니다.

확인은 한 줄이면 된다. 새 규격에만 있는 항목 이름을 파일에서 찾아보면 된다.

```powershell
Select-String -Path src\models.py -Pattern "새로_생긴_항목이름"
```

결과가 비어 있으면 옛 규격이다.

## 4. 재시도가 함수 안에 갇혀 있었다

새 규격에는 「재시도 횟수」를 기록하는 칸이 생겼다. 통신이 한 번에 안 되면 다시 걸어보는데, **몇 번 만에 됐는지를 남기라**는 뜻이다. 결국 성공했더라도 남긴다.

그런데 내 코드에서는 그 숫자를 채울 방법이 없었다. 재시도가 통신 함수 **안쪽**에서 일어나고, 바깥의 기록 담당은 안에서 몇 번 시도했는지 알 도리가 없었다.

```
[기록 담당]  ← 결과만 받음. 몇 번 만에 왔는지는 모름
     ↑
[통신 함수]  ← 여기서 3번 시도하고 마지막 것만 돌려줌
```

세 번 만에 연결된 통화를 "한 번에 됐다"고 적는 셈이다. 결과는 같지만, 회선이 불안정하다는 신호가 사라진다.

성공했을 때는 결과와 시도 횟수를 **같이** 돌려주게 했고, 끝내 실패했을 때는 그 횟수를 오류에 실어서 올려보내게 했다. 파이썬에서는 예외에 값을 담아 보낼 수 있다.

```python
class FetchError(Exception):
    """재시도까지 모두 실패. 사용한 재시도 횟수를 함께 올린다."""
    def __init__(self, cause, retries_used):
        super().__init__(f"{type(cause).__name__}: {cause}")
        self.retries_used = retries_used
```

이제 실패해도 "세 번 시도하고 실패했다"가 남는다.

## 5. 절반 성공을 실패라고 적으면

가장 크게 걸린 건 이거였다.

논문을 여러 쪽에 나눠서 받아오는데, 3쪽까지 잘 받다가 4쪽에서 통신이 끊길 수 있다. 이때 기존 코드는 이렇게 동작했다.

- 이미 받은 3쪽 분량은 **그대로 돌려준다**
- 상태는 **`failed`(조회 실패)**로 적는다

화면 쪽은 `failed`를 보고 "이 사람 조회 실패"로 표시한다. 그러면 **이미 받아온 논문들까지 실패 취급으로 묻힌다.** 있는데 없는 걸로 보인다.

「조용히 실패하지 않기」를 지키려다 **반대 방향으로** 원칙이 깨지는 지점이었다. 실패를 숨기는 것도 문제지만, 성공을 실패로 덮는 것도 같은 종류의 거짓말이다.

그래서 상태를 하나 더 뒀다.

```
partial   불완전 수집 — 받아온 것은 믿을 수 있으나 전부는 아니다
          ① 쪽수 상한에 걸려 미수집분이 남음
          ② 중간에 끊겼지만 일부는 이미 받음
```

배달로 치면 "배송 실패"와 "3개 중 2개 도착"은 다른 말이다. 둘을 같은 칸에 적으면 받은 사람이 상자를 안 열어본다.

다만 이 상태를 **언제 쓰는지**가 팀 규격에 정의돼 있지 않다. 항목 목록에는 추가돼 있는데 설명이 없다. 소스마다 제각각 쓰면 화면에서 합산이 안 되니, 내일 팀에 물어볼 목록에 넣어뒀다.

## 6. 숫자로 확인했다

고친 뒤에 실제로 돌렸다. 일부러 깨진 입력 두 개를 섞었다.

- **공백이 섞인 유효한 ID** → 정규화가 살려내서 정상 조회돼야 한다
- **잘려서 길이가 모자란 ID** → 호출 자체를 하지 않고 「확인 불가」로 떨어져야 한다

```
정상 6 · 확인불가 2 · 실패 0
59건 수집 → 중복 3건 병합 → 최종 56건
검산: 56 + 3 = 59  ✅
```

두 개가 서로 다른 결과로 나왔다. 하나는 살아나고 하나는 막혔다. **의도한 대로 갈렸다는 게 확인의 핵심이었다.** 둘 다 성공하거나 둘 다 실패하면 검증이 아니다.

병합 검산도 넣었다. 최종 건수에 중복 제거 수를 더하면 원 수집 수가 나와야 한다. 안 맞으면 어딘가에서 조용히 사라진 것이다.

## 7. 커밋과 푸시 사이

깃허브로 여러 사람과 협업하는 건 오늘이 처음이었다. 지금까지는 혼자 올리기만 했지 PR이라는 걸 써본 적이 없다.

가장 헷갈렸던 게 **"어디까지가 내 컴퓨터고 어디부터가 팀에 보이는가"**였다.

| 내 컴퓨터에만 남는 것 | 팀에 보이는 것 |
|---|---|
| `add` `commit` `branch` `merge` `rebase` | **`push` 계열** |
| `fetch` `pull` (받아오기) | 깃허브 **웹사이트** 조작 |
| | `gh` 명령 (PR 생성·닫기·병합) |

`commit`까지는 팀에 안 보인다. 이걸 알고 나니 마음이 편해졌다. **커밋은 오히려 안전장치다** — 팀에는 안 보이면서 실수로 파일이 날아가는 걸 막는다. 오늘 만든 것들이 커밋 전까지는 그냥 폴더 안의 파일이라, 브랜치를 잘못 옮기면 그대로 사라질 수 있었다.

공용 파일을 건드리지 않는 요령도 하나 배웠다. 프로브 결과물 폴더를 깃 추적에서 빼고 싶었는데, `.gitignore`는 팀 공용 파일이다. 나 혼자 쓰려고 고칠 수는 없다.

```
.git/info/exclude   ← 이 파일은 깃이 추적하지 않는다. 나만 보는 무시 목록
```

여기에 한 줄 넣으면 공용 파일을 안 건드리고 같은 효과가 난다. 공용 파일 수정은 내일 팀에 요청하기로 했다.

## 8. AI가 한 일 vs 내가 판단한 일

| AI가 한 일 | 내가 판단·검토한 일 |
|---|---|
| 팀 규격과 내 코드를 항목 단위로 대조, 어긋난 곳 목록화 | 어디까지가 내 담당인지 선을 그음 — 남의 파일은 안 건드림 |
| 수정안 작성, 문법·계약 정합성 확인 | 공용 파일 대신 개인 무시 목록을 쓰기로 결정 |
| 실제 API 호출로 동작 검증 | 검산식(최종+제거=수집)을 확인 기준으로 삼음 |
| 커밋 메시지 초안 | 커밋을 두 개로 나눔 — 리뷰어가 볼 것과 근거를 분리 |

### 오늘 내가 판단한 것

- [x] **푸시하지 않기로 했다.** 팀 규격이 방금 바뀐 참이라, 내 해석이 맞는지 먼저 물어보는 게 순서다
- [x] 커밋 작성자에 AI 공동작성자 표기를 **넣지 않았다.** 판단과 검토는 내가 했다
- [x] `partial`을 언제 쓸지는 **내가 정하고, 팀에 확인 요청으로 남겼다.** 규격에 없는 걸 혼자 굳히면 나중에 소스끼리 안 맞는다
- [x] 이 글에 과제 내용·제공 데이터·인물 정보는 쓰지 않았다. 공개 API와 내 코드 이야기만 남겼다

중간에 AI가 "WSL에서는 작업 안 하신 것 같다"고 결론을 냈다가, 가상환경 설정 파일에서 리눅스 경로가 나와 뒤집힌 일이 있었다. **흔적이 없다고 안 한 게 아니다** — 오늘 API에서 배운 것과 같은 종류의 실수였다.

---

세 가지를 고쳤는데 결국 같은 얘기였다. **실패를 실패라고, 절반을 절반이라고, 못 물어본 걸 못 물어봤다고 적는 것.**

숨기지 않는 것만큼이나 부풀리지 않는 것도 어렵다는 걸 5번에서 배웠다. 받은 걸 실패로 덮는 것도 거짓말이었다.

**내일은 팀 회의에서 규격 자체에 대한 제안을 꺼낸다.** 문서 두 곳이 서로 반대말을 하는 지점을 하나 찾았는데, 지금 안 고치면 다음 사람도 나처럼 걸린다. 처음 해보는 종류의 대화라 어떻게 말을 꺼낼지가 코드보다 더 고민된다.
